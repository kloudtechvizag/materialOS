# ADR-020: Platform admin console — a real, separate cross-tenant identity

**Context:** a brief asking for a full platform administration surface (tenants, subscriptions, plans, feature flags, devices, support tickets, audit log, system health) named the single largest architectural gap first: there was no concept of a user who operates *across* tenants at all. Every `User` row is `TenantMixin` (belongs to exactly one tenant) by design, and Postgres RLS (B9) makes every tenant-scoped table return zero rows without a tenant context set. A "platform admin" isn't a bigger set of permissions on the existing model — it's a genuinely different kind of identity, so it needed its own foundation before any of tenants/plans/flags/etc. could be built on top.

**Decision: `PlatformAdmin` is its own table, its own JWT type, its own frontend auth store, with a deliberately small first surface (tenant directory + suspend/reactivate) rather than the full brief.**

- **`platform_admins` table** (migration `b2c3d4e5f6a7`): no `tenant_id`, no RLS — same reasoning as `tenants` itself. No public signup route; `scripts/create_platform_admin.py` creates one, a deliberate operator action rather than self-service.
- **A platform token is structurally distinct, not just differently labeled.** `create_platform_admin_token` omits the `tenant_id` claim entirely (regular tokens always carry one) — `get_db_tenant` can't set an RLS context without it, so a platform token literally cannot be replayed as a tenant token even if a `type` check were skipped somewhere. Verified both directions with real HTTP requests, not just code review: a tenant user's token gets 401 on every `/platform/*` route, and a platform token gets 401 on `/auth/me` (`tests/test_platform_admin.py`).
- **`get_platform_db`** opens a session with no tenant context ever set. Reading anything tenant-scoped (a tenant's `Company` name, its `User` count, its `Subscription`) requires an explicit, one-tenant-at-a-time `set_session_context` call — the exact loop `services/billing_tasks.py`'s daily job already uses to walk every active tenant. This isn't a new way to bypass RLS; it's the same one background jobs already had.
- **Frontend**: `usePlatformAuthStore` persists under a different localStorage key (`materialos-platform-auth` vs `materialos-auth`) than the tenant auth store, `platformFetch` is a separate fetch wrapper (not a parameter on `apiFetch`) so there's no code path where the two tokens could be mixed up. `/platform/login` + `/platform/tenants` + `/platform/tenants/:id` live outside `AppShell`/`PortalShell`, with their own minimal layout — this is MaterialOS-the-company's own tool, not a tenant workspace (spec §56).

**Real scale problem found and fixed, not just described.** This devbox's own database — years of this repo's own test suite runs — has genuinely accumulated **1,460+ tenants**. The first version of `GET /platform/tenants` looped `set_session_context` once per tenant to build the list (the only way to read tenant-scoped data under RLS), unpaginated: **4.05 seconds** for one request, measured with `curl`, not estimated. Added `page`/`page_size` (default 25, max 100) with a `count(*)` against the unscoped `Tenant` table for the total — **92ms** after, re-measured the same way. The per-tenant loop itself wasn't the mistake; doing it for 1,460 rows in one request was.

**What shipped:** platform admin login, tenant directory (searchable, paginated, real company/user-count/plan/subscription data joined per-tenant), tenant detail (adds the plan's granted feature list via `PlanFeature`), and one real write action — suspend/reactivate a tenant (`Tenant.status`). All verified against the actual running `docker-compose` stack (not just `tsc`/tests): logged in as a real created platform admin, listed real tenants, opened a real tenant's detail page, clicked "Suspend tenant" in the real browser, watched the badge and button flip, confirmed in Postgres, reverted it.

**Caught and fixed one real UI bug the same way:** the "Suspend tenant" button initially rendered with white text on a white background — `Button`'s `outline` variant sets no explicit text color and was inheriting `PlatformLayout`'s page-wide `text-white`, invisible until screenshotted and looked at directly. Fixed by giving that one button an explicit `text-foreground`.

**Update — the six deferred items above were all subsequently built** (same "go and build each one" pass), each with its own migration, real tests, and live-browser verification against the running stack:

- **Support tickets.** `support_tickets`/`support_ticket_messages` (migration `c3d4e5f6a7b8`) are the *only* two tables in the whole schema with a platform-bypass RLS clause: `tenant_id = current_tenant OR app.platform_context = 'true'`, that second GUC set only by `get_platform_db` (`set_platform_context`, `app/db.py`). Ticket volume is naturally sparse across tenants, so a real cross-tenant inbox (`GET /platform/support-tickets`) is the actual admin workflow — not the per-tenant loop the tenant directory uses. Tenant side: file/view/reply at `/support`. Platform side: global inbox with status tabs, reply, resolve/close at `/platform/support-tickets`.
- **Tenant archival (soft delete).** `POST /platform/tenants/{id}/archive` takes a real, verified `services/backup.py` (ADR-013) snapshot *before* anything changes, then flags every user of that tenant `is_active=False` and sets `Tenant.status="archived"`. Deactivating users matters more than it looks: `get_current_user` already rejects an inactive user's very next request, so archiving cuts off access immediately — unlike suspension, which (this pass discovered) had no enforcement anywhere. **Real bug fixed as a prerequisite:** `auth.py`'s login and refresh endpoints never checked `Tenant.status` at all; a "suspended" tenant's users could keep logging in and refreshing indefinitely. Both endpoints now reject non-`active` tenants. **Second real bug fixed:** `services/backup.py`'s JSON serializer had no case for Python's `time` type, so archiving (or any backup) of a tenant with HR shift data (`start_time`/`end_time` columns) failed outright — fixed in `_json_default`.
- **Per-tenant audit log viewer.** `GET /platform/tenants/{id}/audit-logs` mirrors the tenant-facing `api/v1/audit.py` query exactly, but reached via the one-tenant-at-a-time `set_session_context` pattern (`audit_log` has no platform-bypass clause — unlike support tickets, "all tenants' audit history in one inbox" was never the use case). UI lives at `/platform/tenants/:id/audit-logs` with a table-name filter.
- **Impersonation.** `POST /platform/tenants/{id}/users/{id}/impersonate` issues a real, working tenant access token — `create_impersonation_token` (`security.py`) reuses the exact `access` token shape `get_db_tenant` expects, plus one extra claim, `impersonated_by`, no normal login token ever carries. Every grant is logged to `impersonation_sessions` (platform-root, `created_by_admin_id`-style FK to `platform_admins`, no RLS) before the token is even returned. The token is short-lived (15 minutes, no refresh token issued at all) and self-identifying: `/auth/me` surfaces `impersonated_by_admin_id`, which `AppShell` uses to render a persistent "you are viewing this workspace as a MaterialOS support session" banner with an "End session" action — there is no way to be impersonating a tenant without the tenant-facing UI itself showing it. A new tab receives the token via a URL *hash fragment* (`/impersonate#token=...&tenant=...`), never a query param or path segment, so it never reaches server access logs.
- **Plan/feature versioned editing.** `POST /platform/plans` is the *only* write endpoint plans get — deliberately no PATCH/PUT on an existing `Plan` row, matching the model's own "immutable, versioned via a new row" design (ADR-014). `services/billing_plans.py::create_plan_version` computes the next `version` for a slug, flips the old row's `is_current` off, and creates every `PlanFeature`/`PlanLimit` row fresh. An existing `Subscription` keeps pointing at its own `plan_id` forever, so a price or feature change can never retroactively reprice or re-scope a live subscriber. UI at `/platform/plans`: cards per current plan, "Create new version" opens a form pre-filled from the current version, with every feature as a checkbox and every limit as a number field (blank = unlimited).
- **In-app admin creation.** `POST /platform/admins` is gated by the *acting* admin re-entering their own current password (`acting_admin_password`, verified against the requester's own `hashed_password` — not the new admin's) — the same "prove it's really you" pattern as GitHub's sudo mode, and the one action in this whole console a stolen-but-unused session token alone cannot perform. Every admin now carries `created_by_admin_id` (migration `e5f6a7b8c9d0`), NULL only for the very first admin bootstrapped via `scripts/create_platform_admin.py`. UI at `/platform/admins` lists every admin and who created them.

**One schema lesson from this pass, worth keeping:** `test_rls.py`'s CI guardrail flags *any* column literally named `tenant_id` as "this table must have RLS enabled" — a correct heuristic that `impersonation_sessions` (platform-root by design, like `platform_admins`/`tenants` themselves, but with a real FK to `tenants`) tripped as a false positive. Fixed by naming the columns `impersonated_tenant_id`/`impersonated_user_id` instead of chasing the check or special-casing the test — a platform-root table's columns just shouldn't be named the way a tenant-scoped table's are.

**Verification (this pass).** 6 new migrations (`c3d4e5f6a7b8` through `e5f6a7b8c9d0`), all applied to the live dev Postgres. 6 new test files (`test_support_tickets.py`, `test_tenant_archive.py`, `test_platform_audit_log.py`, `test_impersonation.py`, `test_plan_versioning.py`, `test_platform_admin_creation.py`), 24 new tests. Full suite: **139 passed**, run inside the real `materialos_api_1` container against the real Postgres. Every feature was also driven live through a real headless-Chromium browser against the running `docker-compose` stack — real signup, real login, real ticket filed and replied to across two separate browser contexts (tenant + platform admin), a real tenant actually archived (watched its active-user count drop to 0 live), a real impersonation token minted and used to reach a real dashboard with the banner rendering, a real plan version bump (Starter v1→v2, price change visible immediately, v1 unchanged), and a real admin created in-app with the created-by chain confirmed via the API.

**Reversibility:** additive, same as the original console. Every new table, endpoint, and frontend route can be removed independently without touching tenant-facing auth, RLS policies, or any pre-existing endpoint — except the `auth.py` tenant-status check and the `backup.py` time-serialization fix, which are real bug fixes to already-shipped behavior (suspend, backups) and should stay regardless of anything else in this ADR.
